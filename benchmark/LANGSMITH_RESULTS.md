## 3. S01 · 평일 오후 4시 식사와 전화 포장

골든셋의 기대값은 `ready`와 제1조·제6조입니다. 제1조에 따르면 공휴일이 아닌 금요일 오후 4시는 브레이크타임입니다. 이 시간에는 매장 식사 주문을 받지 않습니다. 포장 주문은 가능하며 제6조에 따라 앱이나 홈페이지를 이용합니다.

1. 첫 문장의 '공휴일이 아닌'에도 `closed_days` 정규식이 일치합니다. `store_hours`는 '금요일 오후 4시에 매장에서 먹을 수'라는 어형에 일치하지 않습니다. 휴무일과 영업시간이 둘 다 일치해도 명시적인 영업시간 단서가 없으면 `route_questions()`가 영업시간 후보를 제거합니다. 두 번째 문장은 `ordering`으로 처리됩니다. [규칙](../app/services/policy_topics.py#L128) · [분기](../app/services/policy_topics.py#L184)
2. 제2조와 제6조로 두 문장 모두 처리한 것으로 분류됐습니다. `unresolved_parts=0`이어서 첫 문장을 문서 근거로 다시 해결하는 경로에 들어가지 않습니다. 직접 확인한 같은 문장의 하이브리드 검색 후보 1위는 **제1조**입니다. 검색 후보와 작성 단계에 전달한 확정 근거가 달랐습니다. [검색과 미해결 질문 처리](../app/services/policy_search.py#L61)
3. GPT와 Claude의 `retrieve`는 제2조·제6조만 반환했습니다. GPT는 3회 모두 보류했습니다. Claude는 1회 보류했고 2회 매장 식사가 가능하다고 응답해 저장했습니다. 가짜 모델도 3회 제2조·제6조를 인용해 그대로 통과하지 못했습니다.

로컬 대조에서는 '공휴일이 아닌'을 빼면 첫 문장이 미해결로 남고 문서 검색에서 제1조를 찾았습니다. '평일 금요일'이라고 써도 휴무일 우선 규칙이 영업시간 후보를 제거했습니다. '브레이크타임'을 명시하면 제1조가 포함됐습니다. 실제 트레이스 예시는 GPT `01a1e7ef-ad35-790c-8989-ad4618692bef`, Claude `01a1e7f0-b1df-7808-aa52-60b1d632fa4a`입니다.

**수정안.** 요일과 시각이 있고 매장 식사 가능 여부를 묻는 문장은 제1조가 적용되는 후보로 봅니다. '공휴일이 아닌'은 브레이크타임 적용 조건으로 해석하고, 실제 휴무일 문의에 제2조를 적용합니다. S01과 함께 기존 평일 식사 문의 G01, 공휴일 월요일 문의 G03, 화요일 휴무·주차 문의 S02를 확인합니다.

## 4. S04 · 개별 포인트 적립 완료 여부

골든셋의 기대 상태는 `needs_review`입니다. 제26조는 포인트 사용 규정을 설명합니다. 특정 계정의 누락 포인트가 반영됐는지는 계정 상태 확인이 필요한 별도 요청입니다.

1. `STAFF_ONLY`는 실제 좌석이나 환불·픽업 상태는 잡지만 이번 계정 적립 처리 문장은 놓쳤습니다. `POLICY_QUESTION`도 마침표로 끝나는 '있는지 확인해 주세요'에 일치하지 않았습니다. 따라서 포인트 토픽의 문자열 규칙은 맞아도 적용 대상 문의로 처리되지 않았습니다. [직원 확인·문의 규칙](../app/services/policy_topics.py#L20)
2. 결과는 라우팅 토픽 0건, 미해결 문의 0건, `needs_manual_review=false`였습니다. 일반 후기에 쓰는 빈 근거로 작성에 진입했습니다. 끝에 물음표만 붙인 대조 실험은 제26조를 찾았지만 여전히 직원 보류로 들어가지 않았습니다. 일반 포인트 사용 문의는 제26조로, 실제 환불 승인 문의 N05는 직원 보류로 각각 처리됐습니다.
3. GPT와 Claude는 각각 3회 중 2회 `ready`를 반환했습니다. 일부 답글 본문은 매장에서 확인하겠다고 했고, Claude의 한 사례는 `needs_followup=true`도 반환했습니다. 이 필드는 후속 안내입니다. 저장 여부는 `status`가 결정하므로 `ready`인 답글은 저장됐습니다. 가짜 모델은 3회 모두 `ready`였습니다. [그래프의 검토](../app/services/reply_workflow.py#L129) · [저장 상태](../app/services/reply_service.py#L221)

실제 트레이스 예시는 GPT `01a1e7ef-c6be-75c8-abed-7ca257ee11b7`, Claude `01a1e7f0-9e39-7303-9a2a-fd3cc4a67cee`입니다.

**수정안.** 개인 계정·개별 거래와 적립·처리 완료 여부 확인이 결합되면 초안 전에 직원 확인으로 보냅니다. 성공 조건은 `needs_review`, `attempts=0`, 저장할 답글 없음입니다. 실제 상태를 물은 문장과 제26조의 일반 사용 문의를 모두 회귀 검사에 넣습니다.

두 건을 먼저 고쳐 같은 v1을 다시 평가하는 안을 제안합니다. 작성·검토 프롬프트까지 함께 바꾸면 검색·보류 수정의 효과를 판단하기 어려워집니다. 다음 비교에서 이 두 문항의 3회 결과와 기존 35조의 43/44를 먼저 확인합니다.

## 5. 다른 실패의 범위

- **M01, GPT 0/3.** 제12조와 제17조는 올바르게 전달됐습니다. 예제에서는 첫 초안이 직원 확인 플래그를 빠뜨렸고, 두 번째 초안은 오배송의 24시간 안내 문구 검사에서 막혔습니다. Claude는 3/3입니다.
- **M05, GPT 1/3·Claude 2/3.** 제11조·제13조는 전달됐습니다. GPT의 두 보류 모두 `needs_followup`을 넣지 못한 것이 직접 원인입니다. Claude는 한 보류에서 첫 초안이 모델 검토에 걸렸고 재작성에서 `needs_followup`을 빠뜨렸습니다.
- **S02, Claude 1/3.** 제2조·제4조는 전달됐습니다. 모델 검토가 호칭과 질문에 직접 답하는 문장, 규정의 세부 조건을 지적해 두 건이 제한 횟수까지 거절됐습니다. GPT는 3/3입니다.

검토 피드백 원본은 로컬 `failure-traces-v1.json`과 `additional-failure-traces-v1.json`에 보존했습니다. 모델 검토의 판정과 조문 적중을 직접 비교할 때는 각각의 트레이스를 확인합니다.
